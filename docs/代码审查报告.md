# 代码审查报告（Dosage Sync 全量走读）

> 审查日期：2026-09-05 · 方式：旁观者视角全量通读源码（electron 后端 14 文件 + src 前端全部 + 构建配置），未依赖任何历史记忆
> 结论先行：**整体架构合理、主体功能逻辑自洽，无致命缺陷；发现 5 个建议修复的逻辑/一致性问题、若干性能与工程性优化点、以及一批打磨项。** 所有建议均为增量修改，不影响现有功能使用。

## 一、主体功能走读（确认理解正确）

```
数据源适配器（zcode/codex/dsh，antigravity 系已隐藏）
   │  只读各自本地文件 → 归一化 UsageRecord（id = deviceId:source:源内键，天然幂等）
   ▼
本地 SQLite（node:sqlite，WAL）── usage_record / checkpoint（每源锚点）/ meta / device_meta / sync_log
   ▼
四阶段同步引擎：抽取 → 上传（设备 json + 按天分片 jsonl.gz，PUT 整体覆盖）→ 拉取（他机分片合并）→ 合并
   ▼
WebDAV 布局：usage-tracker/devices/<id>.json + usage-tracker/data/<id>/<UTC日>.jsonl.gz
   ▼
Vue3 前端：总览（KPI/趋势/热力图/设备构成）· 明细 · 日志 · 设置
```

**做对的地方（值得肯定）**：
- 记录 ID 全局唯一且稳定（`deviceId:source:源内键`），`INSERT OR REPLACE` 幂等，重复同步不会重复计数；
- 多设备写入天然隔离（各写各的 `<deviceId>/` 目录），无锁也不会互相覆盖；
- 抽取锚点单调不回退 + 24h 回扫窗口，正确处理源端回填/乱序记录；
- 每源独立 checkpoint；切换数据源全链路 `recordScope` 过滤，统计互不污染；
- DSH 库被占用时复制临时副本再读；Antigravity 差值记账的「池成员交集匹配」设计能正确处理池拆合；
- 前端总览加载有 requestId 竞态保护，查询失败保留旧数据 + 可重试横幅；
- 导出 CSV 带 BOM（ipc.cjs:125），Excel 中文不乱码。

## 二、建议修复（P1：影响可靠性或存在误导）

### P1-1 每天「固定时间」同步错过即丢（睡眠/关机不补跑）
- 位置：`electron/backend/scheduler.cjs:38`
- 现状：`d.getHours() === h && d.getMinutes() === m` —— 只有恰好命中那一分钟才触发。tick 间隔 60s，若那一分钟机器正在睡眠、关机或高负载卡过整分钟，**当天不再补跑**。笔记本用户基本必踩。
- 对比：hourly 用的是「流逝时间 ≥ 间隔」的追赶式判断（scheduler.cjs:26），睡眠唤醒后会补跑，是对的。
- 建议：改为 `今日未跑 && 当前时刻 ≥ dailyTime` 的追赶式判断（`today !== lastDailyAt && h*60+m <= nowHour*60+nowMin`），错过后下次 tick 补跑一次。

### P1-2 明细页「设备」下拉可能为空
- 位置：`src/views/DetailView.vue:121` 使用 `usage.devices`，但它**只在 `loadOverview()`（stores/usage.ts:57）里赋值**；DetailView 自己的 `onMounted` 只调 `load()/loadOptions()`。
- 触发场景：当前数据源未启用（此时总览跳过加载，OverviewView.vue:65）或总览加载失败时，先进明细页 → 设备下拉空白，无法按设备筛选。
- 建议：DetailView `onMounted`（或 devices 为空时）自行调一次 `api.getDevices`；或把 devices 加载下沉到 store 独立 action。

### P1-3 日志页的类型/状态筛选器是「假」的
- 位置：`src/views/LogView.vue:30-31` —— 两个 `<select>` 没有任何 v-model / change 处理，选了没反应。
- 建议：要么接上过滤逻辑（kind/level 前端过滤即可），要么暂时移除，避免误导。

### P1-4 导出按钮不遵循筛选条件，与文案矛盾
- 位置：
  - `src/views/DetailView.vue:80-81`：导出按钮就在筛选器旁边，但 `exportData("csv", null, null)` 导出的是**全部数据全部时间**；
  - `src/views/SettingsView.vue:165`：文案写着「导出当前筛选范围的明细」，实际 `exportData(fmt, null, null)` 同样全量。
- 建议：把 DetailView 的当前筛选（模型/供应商/设备/状态）与日期范围传给 `export_data`（后端 `db.exportCsv/exportJson` 已支持 from/to，仅缺明细筛选字段透传）；或把文案改为「导出全部明细」。

### P1-5 config.json 非原子写入，崩溃瞬间可丢配置
- 位置：`electron/backend/config.cjs:121-124` 直接 `writeFileSync`。
- 风险：写一半时进程被杀/断电 → JSON 损坏 → `loadConfig()` catch 后**静默回退默认配置**（config.cjs:114-117），WebDAV 地址账号密码、启用的数据源全部丢失，用户视角是「配置莫名清空」。
- 建议：写临时文件 + `fs.renameSync` 原子替换（两行改动）；损坏时除回退外，把坏文件改名为 `config.json.bak` 留档。

## 三、性能与扩展性（P2：数据量大后会被感知）

### P2-1 每次同步全量重传 + 全量重拉所有历史分片（最大扩展性瓶颈）
- 位置：`electron/backend/sync.cjs:202-218`（上传：`db.getRecords({deviceId, limit:100000})` 全部记录按天分片，**每个日分片每个同步周期都重新 PUT 一遍**）；`sync.cjs:236-270`（下载：PROPFIND 后**把他机所有分片全部重新 GET + 解压 + 重新入库**）。
- 影响：两台机器用一年后，一次同步 = 上传几百个文件 + 下载几百个文件，同步时长随历史线性增长，WebDAV 流量浪费严重。
- 建议（增量、不影响语义）：
  1. meta 表记 `uploadedShards`（日分片名 → 内容 hash 或记录数+最后时间戳），仅当日分片内容变化才 PUT；
  2. 下载侧同理记 `mergedShards`（他机分片名 + 远端 size/mtime 或 hash），未变化的直接跳过。分片名本身含 UTC 日期，旧日期分片一旦稳定几乎不再变化，收益极大。

### P2-2 上传侧 10 万条硬截断
- 位置：`sync.cjs:202` `limit: 100000` 且无分页循环。超过 10 万条后最旧记录不再随上传刷新。
- 现实影响小（旧分片远端已有、覆盖语义幂等），但属于「静默上限」，建议改为按 offset 分页循环取全量，或至少日志里提示截断。

### P2-3 `upsertDevice` 每次调用都全量 UPDATE 设备名
- 位置：`electron/backend/db.cjs:143-147`；调用点 `ipc.cjs:110`（每次 `get_devices`）、`main.cjs:157`（启动）、`sync.cjs:303`。
- 影响：名称没变也会对 `usage_record` 按设备做全表行更新，总览每刷新一次就执行一遍。
- 建议：UPDATE 前先比对 `device_meta` 中现有名称，相同则跳过。

### P2-4 其他（低优先级）
- `sync_log` 无自动清理（仅手动清空按钮），建议保留最近 N 天/条自动裁剪；
- 记录数大后可补复合索引 `(source, started_at)`，现阶段可不做；
- 上传分片为串行 await，可做 3~5 并发（P2-1 落地后总量变小，此项可不急）。

## 四、正确性边界与健壮性（P2/P3）

### P2-5 远端记录校验字段不足，脏分片会让整个同步失败
- 位置：`sync.cjs:261-263` 只校验 `id/deviceId/startedAt` 三个字段；而 `insertRecords`（db.cjs:94-100）中 `deviceName`、`providerId`、`modelId` 为 NOT NULL 且**没有 `?? null` 兜底**。一旦远端分片里混入缺字段的行（手改/半截写入/未来版本），`stmt.run(undefined)` 抛错 → 整个事务回滚 → 整次同步标记失败。
- 建议：校验补齐 NOT NULL 字段，或 `insertRecords` 里给字符串字段加 `?? ""` 兜底。

### P2-6 设备 ID 碰撞无检测（克隆场景互相覆盖）
- 场景：整盘克隆/复制了 `%APPDATA%/DosageSync` 或 `~/.zcode` 到第二台机器 → 两台机器同 deviceId → 每次同步对同一天分片互相整体覆盖，数据乒乓丢失。
- 建议（轻量）：上传 `devices/<id>.json` 前 GET 一次，若已存在且 `bootId`（新加：每次启动随机的 uuid 存 meta）不同，日志告警「检测到设备 ID 被多台机器使用」。低概率但值得留个探针。

### P2-7 Antigravity 快照先落库、记录后入库，中途失败丢消耗
- 位置：`adapter-antigravity-common.cjs:391` 先 `setMeta(snapshotKey)`，记录要等回到 `sync.cjs:172` 才 `insertRecords`；两步之间失败/取消 → 本次差值永久丢失（快照已推进）。
- 现状该源已隐藏，优先级低；恢复该源前建议把「写快照」挪到记录成功落库之后（或 extract 内直接 insert）。

### P2-8 开机自启开关「立即生效但不落盘」的不一致
- 位置：`SettingsView.vue:67-71` 切换即调 `set_autostart`（改 OS 登录项），但配置要等点「保存设置」才写入；不保存就退出 → OS 状态与配置不一致（下次启动 main.cjs:167 会按旧配置纠正，但当次会话是错的）。
- 建议：autostart 只在 `save()` 时统一应用；或切换后自动保存。

### P2-9 WebDAV 细节
- `webdav.cjs:176`：401/403 文案把耗时拼进了「根目录（123ms）」括号里，纯文案 bug；
- `webdav.cjs:14`：endpoint 无 scheme 时默认补 `http://` —— 账号密码会明文走局域网，建议测试连接时对 http 给出明文传输提醒；
- `list()` 的 XML href 解析只认 `d:` 前缀与无前缀（`<ns0:href>` 不识别），对飞牛/Nextcloud 没问题，接其他服务器时留意（webdav.cjs:58）。

## 五、安全（P3，本地工具风险可控但值得做）

1. **WebDAV 密码明文存于 `%APPDATA%/DosageSync/config.json`** —— 建议用 Electron `safeStorage` 加密密码字段（无障碍降级为明文），或至少在文档中声明。
2. `index.html` 无 CSP meta；当前渲染进程无 nodeIntegration、只加载本地内容，风险低，加一条基础 CSP 更稳。

## 六、工程性/一致性（P3：维护成本类）

1. **默认配置三处重复**：`config.cjs:40-69`、`src/stores/app.ts:6-21`、`src/types/index.ts`；**来源名四处重复**：`adapter.cjs`（name）、`ipc.cjs:12-19`（SOURCE_META）、`src/App.vue` AppBar sources、`OverviewView.vue:49-56`（sourceNames）。现在每加一个数据源要改 6+ 处，Antigravity 隐藏时就是 6 处同步注释。建议：来源名统一由 `health_source` 下发（后端已有 name），前端不再硬编码；默认配置至少保证两处中一处为准。
2. **死代码/死配置**：
   - `src/components/SyncProgressBar.vue` 全项目无引用（真·死组件）；
   - `portableMode` 配置项从未被读取（真正生效的是 exe 旁 `portable.flag` 文件，config.cjs:7-14），UI 也无此开关 —— 要么删字段，要么做成真开关；
   - 后端 `Summary.localTokens/remoteTokens` 每次都算，前端无任何消费。
3. **日志 kind 映射缺口**：后端会写 `done`/`error` 两种 kind（sync.cjs:324,308），LogView 的 `kindText`（LogView.vue:9-11）只映射了 extract/upload/download/merge → 界面显示英文原文 "done · 同步完成"。
4. **文档滞后**：docs/方案.md 2.6.5 说趋势图默认「月」，代码实际默认「近七天」（OverviewView.vue:15）；README 口径说明没问题。
5. **版本号恒为 1.0.0**：`get_app_version` 与打包产物都来自 package.json，发新包前记得递增。
6. **设置页改动需手动「保存设置」**：调度/主题/数据源开关都只改内存，离开页面即丢；建议保存前离开时提示，或开关类改动自动保存。
7. **「重新探测」会把 dataDir 永久钉死**（SettingsView.vue:47-48 写入 `s.dataDir`），之后目录迁移不会自动跟随，且 UI 无「恢复自动探测」入口。建议探测结果等于默认目录时写回 `null`。

## 九、结论

主体功能（五源适配、四阶段同步、幂等合并、多维聚合展示）**设计合理、实现干净，没有会导致数据错账的逻辑漏洞**；最值得马上处理的是：固定时间同步错过不补跑（P1-1）、明细页设备下拉空（P1-2）、假筛选与误导性导出（P1-3/4）、配置非原子写（P1-5）。长期跑多台电脑前，优先做 P2-1 的增量上传/下载，否则同步耗时会随历史线性变长。以上全部为增量优化，均不影响你现在的使用方式。

## 二、本轮引入的已知边界（设计权衡，非缺陷）

1. **manifest 最终一致窗口**：对方设备在「分片已传、manifest 未更新」之间崩溃时，新内容延迟到对方下次成功同步才被本端看到（旧方案为全量拉取无此窗口）。定时同步下窗口通常 ≤1 小时。
2. **远端文件被手动删除**：若绕过本工具直接在 WebDAV 服务器上删某分片，本端 `uploaded` 记账会使其不再重传。恢复办法：删除本地库 `meta` 表中 `uploaded:` 前缀记录（或清空缓存目录重新全量）。
3. **DELETE 集合删除**依赖 WebDAV 服务器支持 RFC 4918 递归 DELETE（飞牛 fnOS 支持）；不支持时会收到明确报错且本地数据不受影响。
