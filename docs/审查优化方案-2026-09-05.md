## 二、P0 —— 功能正确性 Bug（建议优先修）

### 1. 便携版「数据跟随 exe」完全失效（证据确凿）
- 位置：`electron/backend/config.cjs:41-48`（`isPortable()` 用 `path.dirname(process.execPath)`）
- 证据：electron-builder 的 `app-builder-lib/templates/nsis/portable.nsi` 把应用解压到 `$PLUGINSDIR\app`
  （%TEMP% 随机目录）后 `ExecWait` 启动，退出时 `RMDir /r $INSTDIR` 删除。便携版运行期间
  `process.execPath` 指向 TEMP 副本，`exe 同目录 portable.flag` 永远检测不到 → 便携模式永不生效，
  数据全部落 `%APPDATA%/DosageSync`，与 `docs/操作.md:30`「数据跟随 exe 同目录」承诺不符。
- 修复：`isPortable()` 改为检测 `process.env.PORTABLE_EXECUTABLE_DIR`（stub 已设置，见 portable.nsi:77），
  `dataDir()` 便携路径基于该变量。

### 2. 便携版 + 开机自启必然失效
- 位置：`electron/main.cjs:170`、`electron/backend/ipc.cjs:178-181`
- 原因：`setLoginItemSettings` 基于 `process.execPath`（TEMP 副本）注册自启，且该副本退出即被删。
- 修复：便携模式下隐藏/禁用「开机自启」开关并提示原因；安装版不受影响。

### 3. 更换 WebDAV 根目录/地址后，本机数据不会重新上传（多机同步数据缺失）
- 位置：`electron/backend/sync.cjs:242-252`
- 场景：用户把 root 从 `/dosage-sync` 改为 `/dosage-sync2`（或换 endpoint）。上传阶段按
  `uploaded:<fileName>` 的内容 hash 记账判断是否跳过——记账与远端无关，内容没变 → 全部分片跳过 PUT，
  新远端只写入 manifest 没有分片；其他设备读 manifest 后逐个 404（`sync.cjs:319-320` `if (!buf) continue`），
  永远合并不到数据，且每次同步重复下载 404。
- 修复（三选一，推荐 a）：
  a. 记账键绑定远端：`uploaded:${endpoint}${root}:${fileName}`；
  b. `save_config` 时检测 endpoint/root 变化，清除 `uploaded:*` 记账；
  c. 设置页提供「强制全量重传」按钮（清 `uploaded:*`）。

### 4. 远端分片字段校验缺 `source`，一条损坏分片可让整次同步失败
- 位置：`electron/backend/sync.cjs:323-327` 校验了 id/deviceId/deviceName/providerId/modelId/startedAt，
  唯独没有 `source`；而 `usage_record.source` 是 NOT NULL（`db.cjs:33`），`insertRecords` 对 source 无兜底
  （`db.cjs:108-114`）。分片里若出现缺 source 的行（手工编辑、磁盘损坏、异常数据），INSERT 抛错 →
  事务回滚 → 异常冒泡到 `run()` 的 catch → 本次同步的后续合并全部终止；该分片不记账，下次同步继续失败。
- 修复：校验清单补 `typeof r.source === "string" && r.source`；同时 `insertRecords` 对 `source` 兜底
  （`r.source ?? "unknown"`）作双保险。

### 5. 「跟随平台」口径是空选项
- 位置：`src/types/index.ts:31-38` 定义了 `platform`（computed_total_tokens）并在设置页渲染第三个 tab
  （`SettingsView.vue:185` 遍历 `TOTAL_MODES`）；但后端 `db.cjs:208-210` 的 `extraExpr` 只区分
  full/非 full，`platform` 实际退化为「简洁口径」，且 `usage_record` 表根本没有 computed_total_tokens 列。
- 修复：短期从 `TOTAL_MODES` 删除 `platform`（一行改动，用户无感知损失）；长期如需该口径再补列。

## 三、P1 —— 健壮性与性能

### 6. 单个数据源抽取失败会中断整个同步
- 位置：`electron/backend/sync.cjs:160-188` 抽取循环没有 per-source try-catch。
- 场景：某源库损坏/被非 WAL 锁占用（实测：非 WAL 库被写锁时只读连接 4ms 内即抛 `database is locked`）
  → 该源抛错 → 其余源不抽取、上传/下载/合并全部跳过，直到该源恢复。
- 修复：循环内 try-catch，失败记 error 日志并继续下一源；整体只要有一个源成功就继续同步流程。

### 7. Codex 适配器每次同步全量读取并解析所有 rollout 文件
- 位置：`electron/backend/adapter-codex.cjs:69-79`。sessions 目录随使用无限增长（每文件可数 MB），
  每次调度同步（含每小时）都要 `readFileSync` + 逐行 JSON.parse 全部历史文件，仅结果被 `since` 过滤。
- 修复：rollout 文件是 append-only，`fs.statSync(file).mtimeMs <= since` 的文件直接跳过即可
  （回扫窗口 24h，安全性足够）。这一行优化可把 Codex 同步从 O(全量) 降到 O(增量)。

### 8. 上传阶段把本机全部记录载入内存 + 分页重复 COUNT
- 位置：`electron/backend/sync.cjs:224-230`（分页 5 万条 push 进 `allLocal`，全量驻留内存）；
  `db.cjs:448` 的 `getRecords` 每页都附带一次 `SELECT COUNT(*)`（同步循环里每页白做一次）。
- 修复：`insertRecords` 前先 `SELECT DISTINCT date(started_at/1000,'unixepoch')` 拿涉及的天，
  按天查询后编码；或给 db.cjs 加免 COUNT 的分页读取接口。数据量十万级以下影响不大，属预防性优化。

### 9. 导出：失败静默、同步阻塞、同名覆盖
- 位置：`ipc.cjs:146-162`（`writeFileSync` 同步写，导出大库会冻结所有 IPC）；
  `SettingsView.vue:83-86`、`DetailView.vue:104-105` 均 `await api.exportData(...)` 但不检查
  返回的 `{ok, message}`——导出失败用户毫无感知；文件名时间戳精确到秒（`ipc.cjs:153`），同秒导出互相覆盖。
- 修复：前端消费返回值并 toast 提示（成功带路径）；写文件改 `fs.promises` + 分批；文件名加毫秒；
  可选 `dialog.showSaveDialog` 另存为。

### 10. WebDAV 请求无重试
- 位置：`electron/backend/webdav.cjs:34-53`。网络抖动一次 → 整次同步失败，等下一轮调度。
- 建议：对幂等操作（GET/PUT/PROPFIND）加 1~2 次退避重试（如 500ms/2s），失败链路更稳。

### 11. 同步失败通知无节流
- 位置：`electron/main.cjs:121-136`。每次失败都弹系统通知，若夜间每小时调度连续失败会连弹多次。
- 建议：只在状态翻转时通知（成功→失败弹一次，失败持续中不再弹，恢复成功可弹一次）。

## 五、实证验证记录

1. **便携版失效**：读 `node_modules/app-builder-lib/templates/nsis/portable.nsi` 全文，确认解压到
   `$PLUGINSDIR\app`、设置 `PORTABLE_EXECUTABLE_DIR=$EXEDIR`、退出 `RMDir /r $INSTDIR`。
2. **SQLite 锁行为**：用 `ELECTRON_RUN_AS_NODE=1`（Node v22.16.0）实测——非 WAL 库被 `BEGIN EXCLUSIVE`
   占用时只读连接 4ms 内抛 `database is locked`（无内建等待）；WAL 库读写互不阻塞。
3. **本机真实数据源**：`~/.zcode/cli/db/db.sqlite` 与 `~/.dsh/tokenledger.sqlite` 均为 WAL 模式、
   `started_at` 均为 integer ms —— 当前锁风险低（P1-6 仍建议修，防库损坏与非 WAL 场景）。
