# 用量同步（Dosage Sync）· 设计方案

> 版本 v1.4 · 状态：已实现
> 关联文档：[操作手册](操作.md) · [README](../README.md)

## 1. 项目定位与目标

一个 **Windows 托盘常驻工具**，解决"多台电脑上 AI 编码工具的 token 用量无法汇总"的问题：

1. 自动读取本机 ZCode、Codex 与 DeepSeek Harness 的模型 token 用量。
2. 以「电脑」为单元，各自上传自己的用量到自建 WebDAV。
3. 拉取其它电脑的用量，在本机汇总展示每台电脑 + 总量。
4. 数据源、存储后端、聚合维度均**不写死**，当前三源可独立启用与筛选。

1. 软件源统一为 `zcode / codex / dsh`，移除 TraeWork 与 WorkBuddy 占位；Codex、DSH 默认停用，由用户在设置页开启。

### 2.9 Antigravity 与 Antigravity IDE 接入（2026-09-05，同日更新为 state.vscdb 快照差值方案）

1. 新增 `antigravity`（旧版，数据在 `~/.gemini/antigravity` 与 `%APPDATA%/Antigravity`）与 `antigravity-ide`（新版，官方名 Antigravity IDE，数据在 `~/.gemini/antigravity-ide` 与 `%APPDATA%/Antigravity IDE`）两个数据源，默认停用；两代目录完全独立，按独立 source 统计，互不影响。**（2026-09-05 起两源暂时从界面与同步流程隐藏，适配器代码保留，恢复见 `electron/backend/adapter.cjs` 注释。）**
2. 两代产品本地均无 token 用量明细文件（用量在 Google 云端，本地仅会话记录）。最终实现弃用「枚举 language_server 进程调本地 RPC」的早期方案，改为读 `%APPDATA%/<应用>/User/globalStorage/state.vscdb` 中缓存的 `antigravityUnifiedStateSync.userStatus`（应用从云端同步的配额状态，软件未运行也可读）：极简 protobuf 解码 → 模型条目（剩余比例 0~1 + 重置时间戳）。
3. 记账为**配额池快照差值法**：同池模型（remaining/resetAt 完全相同，如 Gemini 全系共享一池）合并为一条，池匹配按「成员交集 + resetAt 相同」而非池名；同周期消耗 = 上次剩余 − 本次剩余，池首次出现或周期重置记当前累计 `(1-剩余)×100`，剩余回升不计。快照存 `meta` 表（键 `snapshot:<源id>`），记录 `inputTokens` = 消耗配额点数（非 token），`startedAt` = 同步时间，id 含快照时间戳保证幂等。
4. 优雅降级：文件缺失、数据库被占用（复制临时副本再读）、结构无法解析（旧版格式）时返回空记录并写同步日志，绝不抛出导致整体同步失败。
5. 隔离机制不变：复用 `usage_record.source` 列 + `recordScope` 全链路过滤 + 每源独立 checkpoint 锚点；设备标识取 `~/.gemini/<homeSub>/antigravity_state.pbtxt` 的 `installation_uuid`，取不到走统一回退链。
6. 已知限制：数值单位为配额百分比点（消耗 3.13% 记 3.13）而非 token，仅在该源标签页内自洽；配额比例仅在 Antigravity 联网时刷新，建议用完软件后同步。

### 2.10 健壮性与工程性完善（2026-09-05）

1. 可靠性：每天固定时间同步改为追赶式补跑（睡眠/关机错过当天自动补跑一次）；`config.json` 原子写入（临时文件 + 替换），损坏时留 `.bak` 并回退默认。
2. 增量同步：WebDAV 日分片按内容 sha1 记账（`meta` 表），内容未变化自动跳过上传/下载；每设备新增 `manifest.json`（分片名 → 哈希）供他机增量拉取，旧版客户端自动回退全量遍历并补记账。上传去除 10 万条静默截断（分页循环）。
3. 数据质量：远端记录校验补齐 `deviceName/providerId/modelId`，脏分片不再导致整次同步失败；设备名未变化时跳过存量记录的全量 UPDATE；同步日志自动保留最近 1000 条。
4. 明细页：新增开始/结束日期筛选，导出 CSV/JSON 遵循当前全部筛选条件（设置页导出为明确的全量导出）；明细页设备下拉不再依赖总览页是否加载过。
5. 退役设备清理：侧栏设备项 hover 显示删除按钮，删除时先删 WebDAV 远端数据（失败即中止）再清本地记录与增量记账；禁删本机；同步进行中拒绝删除。
6. 日志页：类型/状态筛选真正生效，补齐 `done/error` 中文分类。
7. 工程性：数据源显示名单一事实源（适配器 `name` 字段 → `list_sources` IPC → 前端渲染），删除前端四处硬编码与 `SOURCE_META`；清理死代码（`SyncProgressBar.vue`、`portableMode` 死配置、`Summary` 中前端未消费的字段）；设置页开关/主题类改动即时生效并自动保存；「重新探测」不再把 `dataDir` 钉死为默认路径；版本号随功能发布递增（1.1.0）。

### 3.1 统计口径（已定稿）

实测：ZCode 的 `computed_total_tokens = input_tokens + output_tokens`，**不含** reasoning 与 cache（例：input 46078 + output 3762 = 49840，reasoning 3330 与 cache_read 45184 均未计入）。因此"累计 token"必须显式定义口径，不能硬编码。

**核心思路：不压成一个"总数"，而是分项展示 + 可配置总量。**

#### 3.1.1 分项指标（UI「用量构成」卡片）

| 指标 | 数据来源 | 说明 |
|---|---|---|
| 净新增输入 | `input_tokens - cache_read_input_tokens` | 未命中缓存、真正新计算的输入 token |
| 缓存命中 | `cache_read_input_tokens` | 输入中命中缓存复用的部分（实测为 `input_tokens` 子集） |
| 输出用量 | `output_tokens` | 正文输出 token |
| 推理用量 | `reasoning_tokens` | 推理模型的思考 token（非推理模型为 0） |
| 缓存写入 | `cache_creation_input_tokens` | 写入缓存的 token（部分 provider 恒为 0） |

#### 3.1.2 总量口径（默认 + 可切换）

- **默认「完整口径」：`input + output + reasoning`**（实测本机 67% 记录含 reasoning、累计 235 万 token ≈ output 的 63.5%，推理是真实计算消耗，不计入会明显低估）。
- 可选「简洁口径」：`input + output`（对齐 ZCode 的 `computed_total_tokens`）。
- 兜底「跟随平台」：直接取 `computed_total_tokens`，供口径校验对照。

#### 3.1.3 缓存命中率

- 定义：`cache_read_input_tokens / input_tokens`。
- 实测：`cache_read_input_tokens` 是 `input_tokens` 的子集（本机 100% 记录满足 `input ≥ cache_read`），本机命中率 ≈ 95.7%（263.7M / 275.6M）。
- 意义：反映重复上下文被缓存复用比例，编码场景通常较高；命中部分计费低，是"实际成本 vs 名义 token"的关键。
- 展示：命中率百分比 + 绝对命中量；输入用量拆分为「净新增输入 = input − cache_read」与「缓存命中 = cache_read」，避免重复计算。

### 3.2 Codex 与 DeepSeek Harness 实测

| 项目 | Codex | DeepSeek Harness |
|---|---|---|
| 默认目录 | `~/.codex` | `~/.dsh` |
| 权威用量来源 | `sessions/YYYY/MM/DD/rollout-*.jsonl` | `tokenledger.sqlite` 的 `session_rollups` |
| 设备标识 | `installation_id` | `.anonymous-user-id` |
| 单次/单行时间 | `event_msg/token_count` 的事件时间 | `day` 对应的本地零点 |
| 记录唯一键 | `deviceId:codex:sessionId:ordinal` | `deviceId:dsh:sessionId:day:site:provider:model` |

- Codex 只采 `info.last_token_usage`，不采累计的 `total_token_usage`；模型名取会话文件内首个 `model` 字段。
- DSH 的 `session_rollups` 是日聚合数据，调用次数按行数统计并忽略 `requests`。数据库可能只有 WAL 中存在最新数据，优先并发只读，失败时复制 db/wal/shm 三件套到临时目录再读取。
- DSH 的原始 `inputTokens` 不包含缓存读取。为满足统一模型中 `cacheReadTokens ⊆ inputTokens` 及 `cache_read / input` 的命中率口径，入库时令逻辑输入为 `inputTokens + cacheReadTokens`；`cacheWriteTokens` 保持独立分项，避免重复计算。

## 4. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 桌面框架 | Electron 35 | 主进程即 Node.js，前后端统一 JS/TS，托盘/自启/单实例原生支持，无 Rust 工具链门槛 |
| 前端 | Vue 3 + TS + Vite + Pinia | 用户熟 Vue；Vite 快；Pinia 管理同步/图表状态 |
| 图表 | ECharts | 一套库覆盖曲线图 + 日历热力图 |
| 本地库 | SQLite（`node:sqlite` 内置） | Node 22 起内置 `DatabaseSync`，免安装、单文件、无原生编译依赖，读 ZCode 库与自建库同一驱动 |
| WebDAV 客户端 | 原生 `fetch` 手写轻量实现 | 协议标准（RFC 4918），手写可控飞牛等兼容性，避免第三方坑 |
| 调度 | `setInterval` 60s 轮询 | 定时上传/拉取，规则简单直接 |

> 唯一前提：本机装 Node.js（构建用）；运行安装版/便携版无需装任何东西（Electron 自带 Chromium 运行时）。

       │                     │

分层职责：

- **数据源适配器**：只负责「从某软件的数据目录抽取 → 归一化为统一用量模型」。
- **同步引擎**：只负责「本地 ↔ WebDAV」的增量搬运与合并去重。
- **本地汇总库**：唯一事实来源，供 UI 查询聚合。

## 6. 统一用量模型

所有数据源归一到如下结构（"不写死"的关键）：

```ts
interface UsageRecord {
  id: string;          // 全局唯一 = `${deviceId}:${source}:${源记录id}`
  deviceId: string;    // 本机统一标识，按既定回退链选取
  deviceName: string;  // 用户起的电脑名
  source: string;      // 软件源："zcode" | "codex" | "dsh"
  providerId: string;  // 供应商
  modelId: string;     // 具体模型
  variant?: string;    // 变体（如 reasoning 档位 low/max/high）
  taskType?: string;
  sessionId?: string;

  // 统一 token 分解（总量在查询时决定）
  inputTokens: number;
  outputTokens: number;
  reasoningTokens: number;
  cacheCreationTokens: number;
  cacheReadTokens: number;

  startedAt: number;   // epoch ms
  completedAt?: number;
  status: string;      // success | error | cancelled ...
}
```

关键设计：**明细层保存原始 token 分解，总量在查询时按口径计算**，这样口径切换不影响已存数据。

## 7. 模型维度体系（解决"模型多、类型不同"）

不同模型类型不同（推理/非推理、不同档位 variant、不同 cache 机制、不同计费），因此采用：

### 7.1 多级分组（从明细向上 roll-up，任意组合）

```
L1 软件源 source      zcode / codex / dsh
L2 供应商  providerId
L3 模型    modelId    GLM-5.3 / deepseek-v4-pro / ...
L4 变体    variant    reasoning 档位 low/max/high ...
附加维度  task_type / agent / mode / session
```

UI 聚合器支持任意维度组合，如"ZCode 全部模型"、"某软件某模型"、"某模型全部变体"。

### 7.2 模型类型元数据表（可扩展配置，不写死）

本地维护一份模型元数据映射，用于分类、排序、图例着色：

```json
{
  "modelId": "GLM-5.3",
  "kind": "reasoning",
  "tier": "flagship",
  "tags": ["bigmodel", "glm"],
  "price": { "inputPerM": 0, "outputPerM": 0 }
}
```

- `kind`：`reasoning`（推理）/ `chat`（对话）/ `flash`（轻量）/ `embedding` / `other`。
- `tier`：`flagship` / `standard` / `flash`。
- 未识别模型自动归入「其他/未分类」，UI 提示可手动归类——未来出现新模型也不写死。

### 7.3 供应商映射与模型别名（实测补充）

- **供应商映射表**：ZCode 的 `provider_id` 多为裸 UUID（如 `ff20a569-…`），UI 无法直接展示。本地维护 `provider_id → 可读供应商名` 映射，未识别 UUID 显示为「未知供应商 + 短 ID」。
- **模型别名规范化**：同一模型存在多种写法（如 `deepseek v4 pro` / `deepseek-v4-pro`、`GLM-5.3` / `glm-5.3`，以及带 `-0731` 日期后缀、`zai-org/` 前缀、`:free` 后缀）。本地维护别名归并表，聚合前先规范化，避免漏计。

## 8. 数据源适配器

```ts
interface DataSourceAdapter {
  id: string;                           // "zcode"
  name: string;                         // "ZCode"
  detect(): Promise<string | null>;     // 自动探测数据目录
  validate(path: string): boolean;      // 目录可达性校验
  extract(since: number): Promise<UsageRecord[]>; // 增量抽取（since=上次水位）
  getDeviceId(): Promise<string | null>;          // 读取设备标识（deviceMid）
}
```

- **ZCode 适配器**：`detect` 找 `~/.zcode`；`extract` 以只读方式打开 `cli/db/db.sqlite`，以「同步锚点」增量读 `model_usage`，映射为 `UsageRecord`。WAL 模式下并发只读安全，不阻塞 ZCode 写入。
- **Codex 适配器**：递归读取 `sessions` 下 rollout JSONL，只采单次 `last_token_usage`，以事件 `ordinal` 保持重扫时 ID 稳定。
- **DeepSeek Harness 适配器**：只读 `session_rollups`，保留 db/wal/shm 临时副本回退，日聚合行映射为统一记录。
- **Antigravity / Antigravity IDE 适配器**：由公共工厂 `adapter-antigravity-common.cjs` 生成（`makeAdapter(id, name, homeSub, appDataName, installMatch, excludeMatch)`）。`detect` 探测 `~/.gemini/<homeSub>` 回退 `%APPDATA%/<appDataName>`；`validate` 校验 `conversations` 或 `User/globalStorage` 存在；`getDeviceId` 返回 null；`extract` 为异步配额快照差值（唯一非文件型数据源，`sync.cjs` 抽取循环已 `await` 兼容）。
- **同步锚点（增量游标）**：`checkpoint` 为每个 source 分别记录 `startedAt` 上限。首次全量抽取，之后覆盖重扫最近 24 小时，兼容 ZCode 回填、Codex 追加与 DSH 当日聚合更新。
- 适配器注册表：启动时加载已安装适配器，未知软件忽略。

## 9. WebDAV 存储后端抽象

飞牛 fnOS、群晖、Nextcloud、坚果云本质都走标准 WebDAV（RFC 4918），差异仅在认证、路径编码、MKCOL 兼容等。因此抽象后端 + 预设：

```ts
interface StorageBackend {
  list(path: string): Promise<Entry[]>;   // PROPFIND
  get(path: string): Promise<string | null>; // GET
  put(path: string, text: string): Promise<void>; // PUT
  ensureDir(path: string): Promise<void>; // MKCOL
}

interface WebDAVBackend {
  endpoint: string;   // https://fn.example.com/dav
  username: string;
  password: string;
  root: string;       // usage-tracker
  preset: WebDAVPreset; // FeiNiu | Nextcloud | Nutstore | Synology | Custom
}
```

- `preset` 只调整路径编码、超时、重试次数、MKCOL 兼容等参数，协议核心一致。
- 未来可新增 `S3Backend` / `OneDriveBackend`，接口不变。

### 9.1 WebDAV 目录布局

```
{用户配置的WebDAV根目录}/
  usage-tracker/
    devices/
      <deviceId>.json          # 设备元信息：电脑名、数据源、最后同步时间
    data/
      <deviceId>/
        2026-09-04.jsonl.gz    # 按"天"分片并 gzip 压缩
        2026-09-03.jsonl.gz
```

**按天分片**：增量同步只追加/补传涉及的天，数据量小、进度可精确计算。分片日期统一按 **UTC** 计算，避免多机本地时钟漂移导致边界错位。

## 10. 同步引擎

### 10.1 同步流程（四阶段，均带进度）

1. **抽取**：遍历所有已启用适配器，按各自锚点增量读取并归一化。
2. **上传**：本机新记录按天分片 PUT 到 WebDAV，逐片进度。
3. **拉取**：拉取其它设备的增量分片到本地汇总库。
4. **合并去重**：以 `deviceId:source:源记录id` 幂等合并，刷新聚合。

### 10.2 去重与冲突

- 唯一键 `id`（含 deviceId），append-only，天然幂等。
- 同一记录重复上传/拉取仅更新不重复计数。
- 设备元信息（电脑名）以最后写入为准。
- **手动同步与定时同步走同一条增量路径**：只抽取 `started_at > 锚点` 的新记录做幂等合并，**不覆盖、不重建历史数据**（历史已上传且可能被他机拉取，覆盖会破坏幂等）。已存在记录的值仅由「最近 N 小时覆盖重扫」更新，其余保持不动。

### 10.3 调度

- 每小时同步默认关闭，可在设置中启用并配置间隔。
- 可选"每天固定时间"（如每天 23:30）。
- 支持"手动立即同步"。
- 断网 → 离线队列；恢复后自动补传。

### 10.4 取消与断点续传

- 同步各阶段均支持「取消」按钮，安全中断：已上传/已合并的分片保留（幂等保证），未完成阶段下次从断点继续。
- 取消不破坏数据：本地库写入走事务（取消即回滚当前事务）；WebDAV 按天分片，中断的 PUT 下次整片重传覆盖。

## 11. 本地汇总库（工具自有 SQLite）

- 表：`usage_record`（统一明细）、`checkpoint`（各适配器同步锚点）、`meta`（本机标识）、`device_meta`（设备信息）、`sync_log`（同步日志）；用户配置独立保存为 `config.json`。
